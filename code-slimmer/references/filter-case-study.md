# 案例：基于两本书生成 Filter 架构优化方案

本案例整理自用户提供截图及“优化 filter 组件架构”聊天中的设计阶段，去除本机路径及项目身份。重点是基于两本书与当前代码生成优化方案；教程是后续单独提出的要求，不是默认交付。

## 原始请求与工作边界

主要请求可概括为：基于 [《软件设计的哲学》第二版](https://github.com/yingang/aposd2e-zh) 和 [《架构整洁之道》](https://cactus-proj.github.io/Clean-Architecture-zh/)，作为架构师生成指定 Filter 源码目录的优化方案。

该请求交付源码诊断、原则依据、目标架构与实施建议，保持组件实现不变。用户之后另行要求转成教程并执行里程碑；这些后续步骤不能反推为初始请求的默认范围。

## 从代码证据提取的问题

该组件已有合理边界：宿主提供业务表单与持久化，组件负责交互；没有必要重写全部架构。

| 原始证据 | 需要解决的问题 | 拟采用的边界 | 验收目标 |
| --- | --- | --- | --- |
| 详情类型允许 `undefined`，选中预设时却用严格快照克隆器复制整份预设 | 类型合法的预设可能被运行时拒绝 | 分别定义查询快照与预设元数据的复制契约 | 合法预设可选中，非法快照仍被拒绝，事件数据隔离保持正确 |
| 多个视图与 hook 分别维护关闭、动画保护和焦点规则 | 修改关闭策略要理解多个位置 | 由一个内部模块持有子浮层生命周期，提供语义操作 | Escape 顺序、主层关闭、焦点恢复和多实例行为正确 |
| 管理插槽暴露容器、层级和动画完成回调 | 业务方需要掌握浮层机制 | 组件提供管理弹窗外壳，宿主提供业务内容 | 调用方简化，关闭和主题行为仍保持正确 |
| 保存完成依赖状态切换与独立错误值；错误的操作来源不明确 | 可能错误关闭面板或显示不匹配的重试入口 | 先明确旧协议判定，再评估显式操作结果 | 成功、失败和重试准确归属于操作，草稿保留符合约定 |
| 示例重复声明快照、预设和节点类型 | 公开契约容易漂移 | 导出消费者需要的少量公共类型，内部类型不外泄 | 示例从包入口复用类型，消费者能够通过类型检查 |

这些结论来自具体实现间的关系，不能只由文件长度或“采用整洁架构”推导。

## 两本书怎样进入方案判断

《软件设计的哲学》的信息隐藏和深模块视角，用于分析浮层知识分散、管理插槽暴露机制等问题；契约定义的视角用于解释合法预设被严格快照克隆器拒绝的问题。

《架构整洁之道》的职责与依赖视角，用于审视宿主业务、组件交互和稳定数据规则的边界，论证纯规则独立验证、外层机制依赖内层规则的设计。

两种视角最终汇入一份方案：当前问题与优先级 → 目标职责和依赖 → 数据、浮层及异步契约 → 分阶段迁移、测试验收与回退。每项建议都需回到当前调用链验证，书中的原则不能代替代码证据。

## 后续请求：怎样转成里程碑

| 原教程阶段 | 学习与修改结果 | 为什么排在这里 |
| --- | --- | --- |
| M0 | 行为地图、测试与可恢复基线 | 先知道哪些外部行为要保住 |
| M1 | 修正预设与快照的克隆契约 | 用最小真实缺陷理解契约边界 |
| M2 | 提取纯规则、独立测试与公共类型 | 为后续交互重组提供稳定基础 |
| M3 | 集中保存校验与完成判定 | 收拢同一业务规则，减少时序约定 |
| M4 | 统一浮层状态与焦点管理 | 在稳定契约上处理交互生命周期 |
| M5 | 封装管理弹窗，简化业务插槽 | 将机制从宿主接口中隐藏 |
| M6，可选 | 迁移到显式异步结果协议 | 收益需要与调用方迁移成本比较 |
| M7 | 结构整理、构建、示例、文档与回退验收 | 检查消费者实际能用，保留恢复路径 |

每关补上修改顺序、局部示例、真实命令、过关条件和常见错误。其他模块可能只需要两三步；没有浮层的模块不需要 M4，没有异步协议歧义的模块不需要 M6。

## 验证数字的解释

设计阶段的聊天记录报告已有 54 项 Chromium 测试通过。这个历史基线说明有现成的交互回归入口；契约冲突仍需要针对性验证。该数字不表示上述设计已实施，也不是本 skill 在新项目中的验收目标。

教程改写的交付报告文档检查及克隆示例验证通过，未修改组件实现。复用时必须重新确认目标代码、配置与命令，不沿用历史通过结论。

## 可迁移的做法

将两本书的设计视角应用到真实调用链，保留合理边界；让每项建议都能追溯到代码证据和适用原则；用调用方需要理解的细节衡量封装；把高成本协议升级标为有条件的选择；交付含迁移、验收与回退策略的优化方案。教程仅在后续请求中展开。
