# Test Slimmer

目标是在保留有价值行为覆盖的前提下降低测试的代码量和维护成本。仅显式调用；普通测试、重构或评审请求不自动套用本流程。

遵循用户本次范围：只要求分析时保持只读；要求精简时直接实施已授权的改动。用户允许削减低价值检查时，可以用明确的覆盖损失换取显著收益。已有提交、推送、PR/MR 指令继续有效；此 skill 本身不增加这些授权。

## 先建立可比较的基线

- 明确模块、分支、比较基线和现有未提交改动的归属。只有用户要求或任务确实需要隔离时才新建分支，不混入无关改动。
- 盘点相关测试入口、共享 helper、fixture、文本快照、图片基线与生成的取证附件。源码、快照和二进制产物分开统计。
- 对受影响范围取得改动前的执行结果；同一任务中已有可信、仍对应当前基线的结果可以复用。记录命令、基线版本、环境、测试名称和结果，避免只保留“通过多少条”。
- 先找重复准备逻辑、大块复制用例、全量 DOM 快照和成功时的截图/附件。别先删已经简短、独立的算法或边界测试。

## 按测试点合并

为准备删除或合并的用例建立简短映射：原测试点 → 最终承载用例/参数行 → 有意放弃的检查及理由。只记录有变化的部分，不另造庞大的维护文档。

相同名称、相同 API 或相同选择器不能证明覆盖重复。核对输入、初始状态、操作路径、断言和边界是否等价，特别是：

- 默认值与显式值、别名入口、受控更新、数据引用身份、错误与取消路径。
- 主题、密度、方向、禁用态、键盘与指针操作，以及真实布局/滚动。
- 样式对象单测与浏览器实际渲染检查：它们可能验证不同层次，不能只按相同颜色或尺寸删除其一。

优先做能直接减少重复的 helper 和参数化。若按功能重新组织 fixture 或套件能明显改善长期维护，也给出这种方案及其改动范围、收益和验证成本；不要只给最小改动，也不要为减少行数强行重构。

## 精简时保住语义

### 复用与参数化

- 抽取稳定、重复的准备动作，例如挂载默认配置、几何 mock、拖拽事件、页面初始化和定位器。预期结果与关键场景差异留在用例附近。
- 每次调用建立新的可变 fixture；保留原有挂载选项、事件顺序、错误处理和清理逻辑。主题、尺寸等用例矩阵可以参数化，但各行仍应有可定位的名称。
- 合并用例前先迁移独有断言，保留原操作路径的重要检查。两个固定列用例合并后，既要验证对齐，也要确认两个方向确实发生滚动。
- 如果 helper 需要越来越多的模式开关、隐藏全局状态，或迫使用例走不同分支，保留少量重复往往更清楚。不要为了少几行压成一个巨型用例。
- 预期值应独立于被测实现。不要从实现返回值生成期望值，把测试改成自我验证。

### 紧凑快照

先确定原快照承担的契约，再选择摘要字段。优先保留可观察内容、必要顺序、交互状态和结构语义；选择哪些字段取决于原测试目的。

表格的合并跨度 `rowspan/colspan`、表单的选中/半选/禁用状态、树的层级或展开状态都可能是核心语义，不能与装饰性 DOM 一起丢弃。非默认值通常可以用很短的标记保留。

- 有专门渲染检查承载时，可以去掉重复的 SVG 路径、包装节点或样式展开；不要笼统声称“浏览器测试已经覆盖全部”。
- 总览页重复嵌入已有独立 demo 时，可保留总览结构检查，让各 demo 承担细节断言。先确认独立覆盖存在。
- 共享 snapshot hook 保持旧调用方默认行为。只更新已审阅的目标快照，并比较未涉及快照是否原样保留。

### 截图与附件

区分有 `toHaveScreenshot` 等断言的图片基线，与仅生成成功取证的截图。后者可改为统一失败时截图；前者仍是覆盖的一部分。

删除截图时检查整个语句和控制流。原来的 `if (...) screenshot()` 不能留下条件，使下一条操作变成条件执行。截图还可能隐式等待动画、字体、布局，或滚动页面；需要的等待应替换为真实就绪条件。

## 验证与归因

- 先运行受影响的测试，再按共享 helper 的影响范围扩展。对最终代码保留一次明确的验证结果；有后续修复时重跑受影响用例，而非无依据反复全量执行。
- 检查实际执行的用例数、参数展开、skip/todo 和断言迁移。数量不变不代表测试点不变；参数化也不应被误记为删除覆盖。
- 出现失败时，区分改动回归、失效测试操作、已有基线问题和环境限制。必要时在隔离目录用原基线的测试/实现，以相同环境复现。若产品实现未变，可以只还原原测试作对照，并说明这个条件。
- 对冷启动、动画或布局等待使用可观察条件与必要的有界超时。不要通过删断言、放宽视觉容差、随意更新图片基线或增加盲目等待来换绿。
- 全量后定向复测通过，应报告“全量 + 定向复测累计结果”，不能写成最终单次全量通过。若没有明确修复而重跑转绿，将其视为可能的波动，不称已修复。
- 已有失败与未验证项单独列出，给出比较基线、相同失败名称/断言等证据。相同实际图片可支持“本次未改变渲染”，但不能证明既有图片差异合理。

用户要求独立审查时，让审查者检查完整基线差异和未跟踪 helper，尤其是删掉的独有断言、摘要快照遗漏及操作顺序。主执行者复核有效问题，修复后做定向复审；不要把未完成或超时的审查当成通过。

## 交付

报告应让用户判断收益和取舍：

- 净减少的源码、文本快照和产物体积，显式计入新增/未跟踪 helper，避免只报删除行数。
- 哪些测试点移入参数化或其他用例；哪些低价值检查确实删除以及原因。
- 最终执行结果、已证实的既有失败、未验证范围，以及独立审查状态（若有）。

只执行已授权的 Git 和远端交付，核验目标分支、提交与远端结果。分析任务不因为有改动建议就自动开始实施。

需要具体示例或解释风险时，读 [匿名复盘案例](references/case-study.md)：它展示净减少 5,680 行的过程，以及审查如何发现摘要快照遗漏的合并跨度。
